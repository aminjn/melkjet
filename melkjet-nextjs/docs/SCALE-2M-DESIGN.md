# طراحیِ مقیاس به ۲ میلیون آگهی — جراحیِ مسیرِ نوشتن و حافظه

> وضعیت: **پیش‌نویسِ طراحی. هیچ کدی هنوز دیپلوی نشده.** این سند قبل از هر تغییری نوشته شد
> تا تصمیم‌ها دیده و سنجیده شوند. هر مرحله جدا، تست‌پذیر و با درِ برگشت است.

## چرا این سند

ما روی ~۵۸ هزار آگهی به دیوارِ کارایی خوردیم (قفلِ سراسریِ `scraper_meta`، `canceling statement`،
ری‌استارت‌های حافظه). هدفِ واقعیِ محصول **۲ میلیون+ آگهیِ کلِ ایران** است. با مدلِ فعلیِ نوشتن،
این غیرممکن است — نه به‌خاطرِ سخت‌افزار (سرور ۴ هسته/۸ گیگ است) بلکه به‌خاطرِ دو الگوریتمِ
`O(کلِ جدول)` که از دورانِ «همه‌چیز یک فایلِ JSON» باقی مانده‌اند.

**نکتهٔ مهم:** این بازنویسی نیست. جدولِ `listings` نرمال و ایندکس‌دار است و مسیرِ خواندنِ
صفحاتِ عمومی از قبل SQLِ درست می‌زند. فقط دو بازمانده باید جراحی شوند.

## ۱. تشخیص — دقیقاً چه چیزی سقف می‌گذارد

### سقفِ ۱ — `mutate()` در هر نوشتنِ کامل، کلِ جدول را می‌خواند
`app/lib/scraper-store.ts:365`:
```
const itemsRes = await c.query('SELECT data FROM listings ORDER BY scraped_at DESC')
```
این داخلِ تراکنش، زیرِ قفلِ `SELECT … FROM kv WHERE key='scraper_meta' FOR UPDATE` اجرا می‌شود،
بعد **تک‌تکِ** آیتم‌ها `JSON.stringify` می‌شوند تا نقشهٔ «قبل» برای diff ساخته شود (خط ۳۷۳).
هزینه = `O(N)` خواندن + `O(N)` سریالایز، با قفلِ سراسری در دست.

- در ۵۸ هزار: ~۱۶۶ مگابایت، ~۲.۵–۴.۳ ثانیه، ~۱ ثانیه CPUِ سریالایز.
- در ۲ میلیون: ~۳۴ برابر → هر نوشتنِ کامل ده‌ها ثانیه، از `statement_timeout=45s` رد → **شکست**.

صدازننده‌های `mutate`ِ کامل (مسیرهایی که این هزینه را می‌دهند):
`insertItems` (اسکرپ)، `addUserListing`/`updateUserListing`/`addItemManual` (ثبت)،
`addArticle`/`updateArticle`/`publishDueArticles` (CMS)، `deleteItem`/`deleteItems`/`clearItems`/
`deleteSource`/`deleteListingsByOwnerPhone`/`reassignListingOwnerPhone`/`requeueAutoRejected`/
`updateOwner`. هر کدام یک full-scan.

### سقفِ ۲ — کلِ آگهی‌ها در heapِ *هر* اینستنس کش می‌شوند
`scraper-store.ts:147` → `pgCache.data.items` یک آرایهٔ کاملِ همهٔ آگهی‌هاست، در هر ۴ اینستنس.
لاگِ `[mem]` (خط ۳۳۵) ثبت کرده که بعد از بار، heap به ~۱GB می‌رسد. منبعش: `listItems`/`buildList`
(خط ۶۱۵–۶۲۹) که آرایهٔ کامل را فیلتر/مرتب می‌کنند.

- در ۲ میلیون: ~۶ گیگ در *هر* پروسه × ۴ = چند برابرِ کلِ رمِ ماشین → **هرگز جا نمی‌شود**.

### سقفِ ۳ (پنهان) — `owners` یک آرایه در یک ردیفِ `scraper_meta`
`insertItems` برای هر آگهی‌دهنده یک `Owner` در `db.owners` می‌سازد (خط ۱۰۳۳) و این آرایه در
همان ردیفِ کوچکِ `scraper_meta` ذخیره می‌شود. در ۲ میلیون آگهی، تعدادِ آگهی‌دهنده‌ها ده‌ها هزار
می‌شود → خودِ ردیفِ متادیتا یک بلابِ چندمگابایتی می‌شود که هر `mutateMeta`/`mutate` بازنویسی‌اش
می‌کند. **همان اشتباهِ تک‌بلاب، این‌بار در متادیتا.** (دقیقاً الگویی که فاز ۲۵۹ و ۲۹۱ برای
advisor و roster شکستند: شاردینگ.)

### چه چیزی مشکل ندارد (تا بی‌دلیل دست نزنیم)
- جدولِ `listings(id, scraped_at, type, status, data, loc_norm)` + ایندکس‌های
  `scraped_at`/`type`/`loc_norm (GIN trigram)` — پایهٔ درستِ رابطه‌ای.
- `listingsByLoc` (خط ۶۵۹) و `candidateListings` (خط ۶۸۷): از قبل SQLِ ایندکس‌دار با `LIMIT`/سهمیه.
- `getItemById` (خط ۷۳۷): کش‌اول، بعد lookupِ ایندکس‌دار — نیمه‌مهاجرت‌شده، الگوی درست.
- فاز ۳۱۷: `mutateSome` قفلِ سراسری را «آخر و ۱ms» می‌گیرد — مسیرِ نوشتنِ هدفمند از قبل مقیاس‌پذیر است.

## ۲. کلیدِ طلایی — dedup از قبل «بلوکه» است

سخت‌ترین بخشِ نوشتن، ضدتکراری است و یک کلیدِ یکتای ساده نیست؛ یک **تطبیقِ شباهتِ فازی** است
(`similarity()`، آستانه ۰.۸۵ روی عنوان+قیمت+متراژ+محله+طبقه+مختصات). ولی `TwinIndex` همین حالا
فقط داخلِ **بلوک** مقایسه می‌کند — `listing-similarity.ts:120`:
```
export function blockKeys(f: SimFields): string[] {
  const ks = []
  if (f.hood) ks.push(`${f.deal}|h:${f.hood}`)           // معامله + محله
  if (f.area) ks.push(`${f.deal}|a:${Math.round(f.area/5)}`)  // معامله + سطلِ ۵متریِ متراژ
  if (!ks.length) ks.push(`${f.deal}|x`)
  return ks
}
```
یعنی برای یافتنِ هم‌ملکِ یک آگهی، لازم نیست کلِ جدول در حافظه باشد — فقط ردیف‌هایی که **حداقل یک
بلوکِ مشترک** دارند لازم‌اند (یک محله + معامله، یا یک سطلِ متراژ + معامله). این مجموعه حتی در ۲
میلیون آگهی چند ده تا چند صد ردیف است، نه میلیون. **این همان چیزی است که dedup را از اسکنِ کل به
lookupِ ایندکس‌دار تبدیل می‌کند.**

## ۳. معماریِ هدف

### ۳.۱ ستونِ `block_keys` + ایندکسِ GIN  ← قلبِ کار
هر ردیفِ `listings` یک `block_keys text[]` می‌گیرد که در **زمانِ نوشتن** از `blockKeys(fieldsOf(item))`
در JS پر می‌شود (منطق پیچیده‌تر از آن است که `GENERATED` پستگرس باشد، ولی ساده است که در همان
upsert نوشته شود). ایندکس:
```
CREATE INDEX listings_block_keys ON listings USING gin (block_keys);
```
تابعِ تازه `candidatesByBlocks(blockKeys[]): Item[]` فقط ردیف‌های هم‌بلوکِ `listing` و غیرِ
`duplicate/rejected` را می‌کشد:
```
SELECT data FROM listings
 WHERE type='listing' AND status NOT IN ('duplicate','rejected')
   AND block_keys && $1::text[]
```
سپس `TwinIndex` فقط روی همین کاندیداها ساخته و `find` می‌شود.

- `findPublicListingTwin` (خط ۱۰۶۷): به‌جای `load().items` کامل → `candidatesByBlocks`.
- `insertItems`/`addUserListingCore`/`publishUserListingsBatch`: به‌جای ساختِ `TwinIndex` روی کلِ
  `db.items`، ایندکس را از کاندیداهای بلوکِ ورودی‌ها می‌سازند. (در دسته، بلوک‌های همهٔ ورودی‌ها
  یک‌بار جمع و یک کوئری زده می‌شود.)
- کلیدِ دقیقِ `url|title` (خط ۹۳۱) هم به یک lookupِ ایندکس‌دار تبدیل می‌شود (ستون/ایندکسِ
  `exact_key` یا `WHERE data->>'url' = …`). این مسیرِ «همان آگهی دوباره اسکرپ شد» است.

**درِ برگشت:** اگر `block_keys` خالی/غایب بود (ردیفِ قدیمیِ هنوز backfill‌نشده)، مسیر به رفتارِ
امنِ قبلی برمی‌گردد (کاندیدا نمی‌دهد = درجِ نو؛ بدترین حالت یک تکراریِ ناگرفته، نه فساد).

### ۳.۲ حذفِ تدریجیِ کشِ کاملِ heap
هر مسیری که الان `load().items` کامل را می‌خواند، به یک کوئریِ هدفمند تبدیل می‌شود:
- شمارش‌ها (`countActiveListingsOf`) → `SELECT count(*) … WHERE`.
- فهرست‌های فیلترشده (`listItems`, `listArticles`, `pendingForModeration`) → کوئریِ ایندکس‌دار با
  `WHERE`/`LIMIT`/`OFFSET` (همان الگوی `listingsByLoc`).
- تک‌آیتم‌ها (`getArticleBySlug`) → `WHERE data->>'slug' = …` با ایندکس.

این **آخرین و پرریسک‌ترین** مرحله است، چون صدازننده‌های `listItems` در کلِ کدبیس پخش‌اند
(رندرِ صفحات، آمارِ بازار، سایت‌مپ، موتورِ مشابه‌ها). census کامل لازم است (بخشِ ۵) و هر صدازننده
جدا مهاجرت و تست می‌شود. تا پایانِ این مرحله، کشِ heap به‌عنوانِ fallback می‌ماند.

### ۳.۳ `owners` به جدول (شاردینگ — الگوی فاز ۲۵۹/۲۹۱)
آگهی‌دهنده‌ها از آرایهٔ داخلِ `scraper_meta` به جدولِ `owners(id PK, phone, name, count, first_seen)`
یا کلیدِ شاردِ `owner:{phone}` منتقل می‌شوند. dedupِ مالک (خط ۱۰۳۲) به lookupِ ایندکس‌دار روی
phone/name تبدیل می‌شود. این ردیفِ `scraper_meta` را دوباره کوچک و سبک نگه می‌دارد.

### ۳.۴ متادیتا و rev به‌شکلِ مقیاس‌پذیر
- `rev` و چکِ اعتبارِ کش از قبل می‌توانند از **Redis** بیایند (`scraper_rev`، خط ۳۰۴/۳۳۷/۴۱۰).
  در مقیاسِ میلیونی، Redis به‌جای `SELECT kv FOR UPDATE` برای شمارندهٔ rev پیشنهاد می‌شود (فعلاً
  اختیاری است؛ `REDIS_URL`).
- `categories` (خط ۵۵۷) که الان با اسکنِ آیتم‌های دایرکتوری مشتق می‌شود → `SELECT DISTINCT
  data->>'category' … WHERE type='directory'` با ایندکس، یا نگه‌داریِ افزایشی.

## ۴. نقشهٔ مرحله‌ای (هر مرحله جدا دیپلوی و برگشت‌پذیر)

| مرحله | کار | ریسک | سنجهٔ موفقیت |
|---|---|---|---|
| **A** | ستونِ `block_keys` + ایندکسِ GIN؛ پرکردن در زمانِ نوشتن؛ backfillِ تدریجیِ ردیف‌های موجود (اسکریپت، دسته‌ای). **بدونِ تغییرِ رفتار** — فقط ساختِ داده. | کم | `block_keys` روی ردیف‌های تازه پر می‌شود؛ backfill بدونِ قفلِ طولانی تمام می‌شود. |
| **B** | مسیرهای dedup (`findPublicListingTwin`, `insertItems`, `publishUserListingsBatch`) از `candidatesByBlocks` بخوانند — **پشتِ فلگِ env**، با **تستِ هم‌ارزی** (همان ورودی، همان حکمِ تکراری/نو که مسیرِ قدیمی می‌داد). | متوسط | روی دیتابیسِ پر، مجموعهٔ تصمیم‌های dedup ۱۰۰٪ با مسیرِ قدیمی یکی است؛ زمانِ `insertItems` مستقل از اندازهٔ جدول. |
| **C** | `owners` به جدول/شارد؛ dedupِ مالک lookupِ ایندکس‌دار. مهاجرتِ تنبلِ copy-if-absent، بلابِ قدیمی به‌عنوانِ بکاپ. | متوسط | ردیفِ `scraper_meta` کوچک می‌ماند؛ مالکِ موجود درست پیدا می‌شود. |
| **D** | حذفِ تدریجیِ کشِ heap: صدازننده‌های `listItems` تک‌به‌تک به SQL. کش تا پایان fallback می‌ماند. | **زیاد** | heapِ اینستنس مستقل از اندازهٔ جدول؛ هیچ مسیری کلِ جدول را به حافظه نمی‌آورد. |

مسیرِ `mutate`ِ کامل برای عمل‌هایی که ذاتاً روی کلِ جدول‌اند (مثلِ `requeueAutoRejected`,
`clearItems`) یا به SQLِ مجموعه‌ای (`UPDATE … WHERE`) تبدیل می‌شوند یا دسته‌ای/صفحه‌بندی‌شده
می‌گردند — این‌ها نادر و ادمینی‌اند، پس اولویتِ آخرند.

## ۵. census صدازننده‌ها (از اسکنِ کاملِ کدبیس)

### ۵.۱ نوشتن — `mutate`ِ کامل **ماژول-خصوصی است**
`mutate` export نمی‌شود (خط ۳۵۲)، پس **تنها صدازننده‌هایش داخلِ همین فایل‌اند** — سطحِ نوشتنِ
کامل بسته و قابلِ‌کنترل است:
`insertItems` (اسکرپ)، `addUserListing`/`updateUserListing`/`addItemManual` (ثبت)،
`addArticle`/`updateArticle`/`publishDueArticles` (CMS)، `deleteItem`/`deleteItems`/`clearItems`/
`deleteSource`/`deleteListingsByOwnerPhone`/`reassignListingOwnerPhone`/`requeueAutoRejected`/
`updateOwner` (ادمینی/دسته‌ای). مسیرهای داغِ ممیزی/ویرایش/وضعیت/مختصات/معامله/publish از قبل روی
`mutateSome`/`mutateMeta`اند (فاز ۳۱۷) — مقیاس‌پذیرند.

### ۵.۲ خواندن — صدازننده‌های `listItems` (مرحلهٔ D، بزرگ)
`listItems`/`listItemsStable`/`getItemById(کش)`/`pendingForModeration`/`listArticles`/
`getArticleBySlug`/`countActiveListingsOf`/`findPublicListingTwin` همه از آرایهٔ heap می‌خوانند.
صدازننده‌های بیرونی (نمونه، نه کامل): رندرِ `app/[site]`, `app/search`, `app/blog/*`,
`home-data`, و ده‌ها مسیرِ `app/api/*` (directory/reos/crm/stats/telegram…). این بخش پخش است و
هر صدازننده باید جدا به کوئریِ `WHERE/LIMIT` یا `COUNT` مهاجرت کند.

### ۵.۳ خطرناک‌ترین‌ها — خواننده‌های تحلیلیِ «کلِ پیکره» (قلبِ مرحلهٔ D)
این‌ها نه صفحه‌بندی دارند نه فیلتر؛ کلِ آگهی‌ها را می‌خوانند و پردازش می‌کنند. در ۲ میلیون
این‌ها اول می‌ترکند (یکی‌شان از قبل `statement timeout` خورده):
- **`market-stats.ts`** — `records()` و `soldStats` روی **همهٔ** آگهی‌ها آمار می‌سازند؛ لاگِ
  CLAUDE.md همین‌جا `57014 statement timeout` ثبت کرده. → باید به **SQL aggregate** (میانه/میانگینِ
  هر سلولِ شهر|محله|معامله|نوع) با ایندکس تبدیل شود، یا جدولِ آمارِ ازپیش‌محاسبه (materialized).
- **`listing-dedupe.ts`** (`dedupeListings`/`buildDupIndex`/`findDuplicateOf`) — جاروی O(n²) روی
  کلِ آگهی‌ها (کرونِ اینستنسِ ۰، خطرِ شناخته‌شدهٔ CLAUDE.md). → همان کاندیداگیریِ بلوکیِ §۳.۱.
- **`listing-writer.ts:53`** — ساختِ پیکرهٔ واژگان از متنِ همهٔ آگهی‌ها + enrichment. → نمونه‌گیری/صفحه‌بندی.
- **`sitemap-store.ts`** (listings/articles/directory) — شمارشِ همهٔ URLها. → صفحه‌بندیِ sitemap (sitemap index).
- **`platform-stats.ts`** — ۵ بار خواندنِ کامل فقط برای `.length`. → `SELECT count(*) … GROUP BY type`.
- **`reos/territory-sync.ts`, `reos/area-stats.ts`, `area-insight.ts`** — اسکنِ کاملِ استخرِ عمومی.
  → SQL aggregate per سلول.
- **`moderation.ts:273,330`** — صفِ ممیزی و اسکنِ «منتظرهای گیرکرده». → `WHERE status='pending' LIMIT`.
- **`directory/route.ts`** و **`telegram-notify`/`alerts-runner`/`cron-runner`** — فست‌های دایرکتوری و
  تطبیقِ مشترکان روی کلِ استخر. → کوئریِ هدفمند/ایندکس‌دار.

### ۵.۴ یک موتورِ dedupِ دوم که **نباید** قاطی شود
`app/lib/duplicate-check.ts` یک ضدتکراریِ **جداگانه و محدود به حوزهٔ مشاور** است (نه موتورِ
twinِ عمومی): میدان‌هایش فرق دارند (`neighborhood/area±6%/price±10%/rooms/title`) و دامنه‌اش را
از `advisor-store` می‌گیرد نه از جدولِ `listings`. این در طراحیِ بلوکیِ §۳.۱ دست‌نمی‌خورد — فقط
ثبت شد تا با موتورِ عمومی اشتباه نشود.

### ۵.۵ متادیتا — چه چیزی افزایشی است و چه چیزی اسکن
- `sources` و `owners`: **افزایشی** (داخلِ `insertItems`/`addUserListingCore` ساخته می‌شوند؛ اسکن نمی‌خواهند).
  ولی `owners` یک آرایه در یک ردیفِ `scraper_meta` است (سقفِ ۳) → باید جدول/شارد شود (§۳.۳).
- `categories`: `categoriesOf` (خط ۵۵۷) بخشِ ذخیره‌شده را افزایشی دارد ولی **در هر خواندن کلِ
  `db.items`ِ دایرکتوری را اسکن می‌کند** → `SELECT DISTINCT data->>'category' WHERE type='directory'` با ایندکس.

## ۶. تستِ بارِ همزمان — درسِ تلخِ `8a61d73`

یک‌بار یک «فیکسِ ریشه‌ای» (پیش‌خواندنِ بیرونِ قفل) روی تستِ تک‌رشته‌ای سبز بود ولی زیرِ بارِ
همزمانِ تولید ۵۰۴ داد و سایت را خواباند. پس هیچ مرحله‌ای بدونِ این‌ها دیپلوی نمی‌شود:
1. **دیتابیسِ آزمایشیِ پر**: seedِ ۰.۵–۲ میلیون ردیفِ ساختگیِ واقع‌نما (توزیعِ محله/قیمت/متراژِ
   مشابهِ تولید) تا بلوک‌ها اندازهٔ واقعی داشته باشند.
2. **شبیه‌سازِ چنداینستنسی**: چند نویسندهٔ همزمان (اسکرپ + ممیزی + publish) مثلِ ۴ اینستنسِ تولید،
   تا رقابتِ قفل دیده شود — نه فقط یک رشته.
3. **سنجهٔ قبل/بعد**: زمانِ `insertItems`، صفِ `pg_stat_activity`، heapِ پروسه، و زمانِ پاسخِ صفحه.
   هر مرحله باید سنجه را بهتر (یا دستِ‌کم ثابت) کند، با داده نه ادعا.
4. **تستِ هم‌ارزیِ dedup**: خروجیِ مسیرِ بلوکی باید برای مجموعهٔ ثابتی از ورودی‌ها دقیقاً همان
   حکمِ مسیرِ قدیمی را بدهد (added/dup/updated).

---

## ۷. ریسک‌ها و درهای برگشت

- **خطای block_keys ناقص** → کاندیدا کمتر از واقع → یک تکراریِ ناگرفته (نه فساد؛ ادمین merge می‌کند).
  مهارش: هر دو بلوک (محله و متراژ) با هم؛ و تا پایانِ backfill، مسیرِ قدیمی fallback.
- **هر مرحله فلگ‌دار** (`env`): یک خط برمی‌گرداند به رفتارِ قبلی، بدونِ ری‌دیپلوی.
- **مرحلهٔ D پرریسک‌ترین است** — تا census کامل و هر صدازننده تست‌شده نباشد، شروع نمی‌شود؛ کش
  fallback می‌ماند.
- **بدونِ دیپلویِ وسطِ کار**: هر `pm2 reload` کارِ زندهٔ اینستنسِ ۰ را می‌کُشد (درسِ فاز ۲۷۸)؛
  دیپلویِ هر مرحله وقتی صف خالی است.

## ۸. جداسازی از مسکّنِ امروز

پروندنِ ۱۱ هزار آگهیِ کهنه (DELETE روی `type='listing'` قدیمی‌تر از ۴۵ روز، `__dealStatus IS NULL`)
یک **مسکّن** است تا همین حالا آن ۸ آژانسِ گیرکرده راه بیفتند — جدول را ~۲۰٪ کوچک و قفل را کوتاه‌تر
می‌کند، ولی سقفِ `O(جدول)` را برنمی‌دارد. این سند راهِ برداشتنِ خودِ سقف است. دو کار مستقل‌اند.
